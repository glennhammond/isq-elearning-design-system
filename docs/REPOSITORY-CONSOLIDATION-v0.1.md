# Repository consolidation plan v0.1

- **Product:** eLearning Design System
- **Status:** Audit complete; migration staged
- **Date:** 3 September 2026
- **Canonical candidate:** `glennhammond/isq-elearning-design-system`

## Executive decision

Use the current `isq-elearning-design-system` repository as the technical baseline. It has the most mature content model, generator, governance records, validation scripts, component catalogue and active custom-block/xAPI work.

Do not combine the three repositories by copying every file. The older repositories contain generated derivatives, duplicate assets, placeholder material and font binaries that should not be propagated. Consolidation means preserving useful thinking and evidence inside one maintained system, then retiring redundant implementations.

## Repository inventory

| Repository | Current role | Audit finding | Disposition |
|---|---|---|---|
| `isq-elearning-design-system` | Governed static reference site and active custom-block library | Strongest architecture; 111 files on the Phase 03 branch; structured JSON sources, Jinja templates, validators, governance records and current qualification work | Retain as canonical technical baseline |
| `eLearning-design-system` | Older static design-system site | 411 files, including 313 SVGs, 46 PNGs, 22 HTML pages and bundled font files; useful early concepts mixed with thin, placeholder and outdated implementation material | Extract selected concepts and evidence; retain temporarily as a legacy source |
| `elearning-design-system-react` | Anima-generated React conversion | 602 files; autogenerated Vite/React structure; shares at least 73 identical assets with the older static repository and adds no stronger content authority | Do not merge generated code; archive after verification |

## Security and privacy observations

All three repositories were public at the time of this audit.

A focused scan of the current Phase 03 custom-block and CI files found no embedded Basic authentication value or production credential. Qualification files contain explicit placeholders and a named test endpoint. This focused scan is not a complete historical secret audit.

Before final consolidation:

- run a full current-tree and Git-history secret scan;
- keep LRS credentials and learner identity outside reusable browser components;
- rotate any credential that may previously have been committed, even if the repository is later made private;
- decide separately whether GitHub repositories and Vercel deployments should be public, private or access-controlled;
- do not copy licensed font binaries into the canonical repository.

## Target information architecture

The existing generator and structured-data approach remain. The system should evolve towards these visible domains without an unnecessary framework rewrite:

- Product overview
- Learning and experience principles
- Foundations
- Components
- Course compositions
- Imagery and multimedia
- Accessibility and quality
- Platforms
- Telemetry and xAPI
- Themes
  - ISQ
- Applications
  - Child Protection for Teachers
  - Child Protection for Principals and Board Directors
  - Domestic and Family Violence
  - Psychosocial Risk Learning
- Governance, evidence and releases
- Resources and asset registry

Course applications may demonstrate the system but must not silently become reusable component specifications or replace approved source documents.

## Safe execution sequence

### Phase 0: Establish authority

- Record the product-boundary decision.
- Record this consolidation inventory.
- Keep repository visibility changes outside the consolidation branch.

### Phase 1: Protect current work

- Preserve the stacked Phase 02 and Phase 03 branches and draft pull requests.
- Complete or explicitly defer their evidence gates.
- Avoid repository renaming while review URLs and preview deployments are active.

### Phase 2: Reconcile legacy content

- Compare each useful legacy concept with the current structured sources.
- Rewrite only where needed to create an accurate, reusable system record.
- Record provenance and the reason for retain, replace or retire decisions.
- Do not import the Anima-generated codebase or licensed font binaries.

### Phase 3: Broaden the current system

- Change the outer product identity to eLearning Design System.
- Add an explicit ISQ theme and implementation section.
- Preserve `.isq-` component contracts inside that layer.
- Add Figma course-composition references and future code connections.
- Add a controlled asset registry rather than a bulk asset dump.

### Phase 4: Migrate repository identity

After the current development gates are stable:

1. rename `eLearning-design-system` to a clear legacy name;
2. rename the canonical repository to `eLearning-design-system`;
3. verify remotes, links, Actions, branch references and collaborator access;
4. update the Vercel Git connection and project name;
5. verify preview and production deployment behaviour;
6. archive the two legacy repositories only after the retained material is traceable in the canonical system.

### Phase 5: Verify and close

- build and validate the generated site;
- check internal links and search;
- inspect representative desktop and mobile pages;
- confirm no production secrets or restricted source content are present;
- document the final canonical repository, Figma file and deployment URLs;
- retain a rollback route until the renamed project is stable.

## Definition of done

Consolidation is complete when:

- one repository is declared and used as the canonical source;
- the product is named eLearning Design System;
- ISQ is represented as a theme and implementation rather than the entire product boundary;
- useful legacy concepts are reconciled with recorded provenance;
- redundant generated implementations are archived;
- GitHub and Vercel point to the same maintained source;
- the Figma system and coded components have a documented relationship;
- active component maturity and QA evidence remain truthful;
- repository and deployment visibility are deliberate rather than inherited defaults.
